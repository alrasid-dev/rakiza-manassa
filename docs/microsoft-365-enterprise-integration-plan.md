# خطة الإدخال المؤسسي للمنصة في Microsoft 365

> **الغرض:** توضح هذه الخطة المسار الآمن لتحويل المنصة الداخلية الموحدة للمتابعة اليومية من وضع الدخول المؤقت إلى تشغيل مؤسسي داخل Microsoft 365، مع توزيع واضح للمسؤوليات وبوابات اعتماد تمنع إدخال بيانات المحكمة الحساسة قبل اكتمال الضوابط اللازمة.

## نطاق الخطة والنتيجة المستهدفة

تظل المنصة تطبيق ويب مستقلاً بواجهة عربية، ثم تُتاح داخل Microsoft Teams كتطبيق داخلي شخصي يحمل الرابط نفسه. تُستبدل المصادقة المؤقتة تدريجياً بمصادقة Microsoft Entra ID للمستأجر المؤسسي، وتبقى صلاحيات المنصة التشغيلية مستقلة داخل قاعدة بياناتها ولا تُشتق تلقائياً من ألقاب Entra أو Teams. يعتمد تسجيل الدخول المؤسسي على OpenID Connect؛ تصدر منصة Microsoft identity platform رموز الهوية وتوفر مستندات الاكتشاف ومفاتيح التوقيع تحت نطاق المستأجر. [1]

لا يضيف Teams صلاحية مستقلة للوصول إلى بيانات المحكمة؛ بل يكون **قناة عرض** للتطبيق نفسه. أما Copilot Studio فيبدأ كوكيل معرفي محدود بدليل المستخدم والسياسات العامة فقط، من دون اتصال مباشر بقاعدة بيانات المنصة أو بملفات القضايا.

| المسار | النتيجة التشغيلية | لا يبدأ قبل |
|---|---|---|
| تشغيل الويب الإنتاجي | نطاق HTTPS ثابت للمنصة | اعتماد مالك المنصة ومالك الأمن |
| Entra ID | دخول بالحساب المؤسسي مع MFA وسياسات وصول مشروط | تسجيل تطبيق ومراجعة الردود والأذونات |
| Teams | تطبيق داخلي شخصي يعرض المنصة | النطاق الثابت وموافقة مسؤول Teams |
| Graph Mail | رسائل بريد مرحلية من صندوق خدمة معتمد | موافقة أمني البريد وبيانات التطبيق السرية |
| Copilot Studio | وكيل معرفي محدود في Teams أو Microsoft 365 Copilot | موافقة مالك المعرفة ومسؤول Power Platform |

## المرحلة الأولى: اعتماد التشغيل الإنتاجي وحدود البيانات

يُنشئ مالك المنصة نقطة تفتيش ثم ينشر النسخة للحصول على نطاق إنتاج HTTPS ثابت. بعد ذلك تُستبدل قيمة `__PUBLISHED_DOMAIN__` داخل حزمة Teams باسم النطاق المنشور فقط. لا ينبغي إدخال عناوين القضايا أو ملفاتها أو بيانات الأشخاص الحساسة في وصف تطبيق Teams أو بياناته التعريفية.

قبل ربط أي خدمة مؤسسية، يحدد مسؤول أمن المعلومات **تصنيف البيانات** لكل وحدة: بيانات عامة داخلية، بيانات تشغيلية مقيدة، وبيانات قضائية حساسة. تبقى التجارب الأولية في بيئة بيانات غير حساسة. ويجب أن تكون هناك جهة مالكة للأمن قادرة على إيقاف الوصول أو سحب التراخيص أو إلغاء التطبيق من Teams عند الضرورة.

## المرحلة الثانية: المصادقة المؤسسية عبر Microsoft Entra ID

يسجل مسؤول Entra تطبيق ويب أحادي المستأجر للمحكمة. يجمع التطبيق هوية المستخدم عبر OpenID Connect؛ وتلزم مطابقة عناوين إعادة التوجيه المسجلة حرفياً مع عنوان التطبيق الإنتاجي. توصي Microsoft بالتحقق من توقيع رمز الهوية وادعاءاته باستخدام مكتبة تحقق موثوقة، وبالتحقق من `state` و`nonce` لمنع إساءة استخدام تدفق الدخول. [1]

| عنصر الإعداد | المسؤول | القرار أو القيمة المطلوبة |
|---|---|---|
| نوع الجمهور | مسؤول Entra | مستأجر المحكمة فقط، وليس جمهوراً عاماً متعدد المستأجرين |
| عنوان إعادة التوجيه | فريق المنصة | مسار دخول الإنتاج ومسار الرجوع الآمن بعد Teams عند الحاجة |
| المطالبات المسموح بها | أمن المعلومات + الموارد البشرية | `oid` و`tid` والبريد المؤسسي والاسم فقط، مع تجنب مطالبات غير لازمة |
| MFA والوصول المشروط | أمن المعلومات | فرض MFA ومنع الدخول من سياقات غير معتمدة وفق سياسة الجهة |
| ربط الحساب الداخلي | مالك المنصة | ربط معرف Entra بالملف التشغيلي بعد موافقة، وليس تلقائياً من اسم العرض |
| الصلاحيات التشغيلية | مالك المنصة | تبقى `full_control` و`general_view` و`employee` و`trainee` داخل المنصة وسجل تدقيقها |

يُنفذ الربط على مرحلتين. في المرحلة التجريبية، يحول الدخول المؤسسي المستخدم إلى طلب ربط بملفه ويحتاج اعتماد مالك المنصة. وفي المرحلة اللاحقة، يمكن اعتماد الربط التلقائي للبريد المؤسسي فقط بعد اختبار عدم وجود تكرار أو تعارض في الملفات. لا يمنح نجاح تسجيل الدخول أي صلاحية إدارية بحد ذاته.

## المرحلة الثالثة: إدخال تطبيق Teams وتوزيعه

بعد النشر، يراجع مسؤول Teams حزمة التطبيق والنطاقات المسموح بها ثم يرفعها أو يوافق عليها من مركز إدارة Teams. يوفر مركز الإدارة التحكم في الإتاحة على مستوى المؤسسة أو مستخدمين ومجموعات محددة، مع توصية Microsoft باستخدام أدنى دور إداري قادر على المهمة. [2]

| خطوة التسليم | المنفذ | دليل الإثبات المطلوب |
|---|---|---|
| استبدال نطاق الحزمة | مالك المنصة | نسخة ZIP تتضمن نطاق الإنتاج فقط |
| رفع أو إتاحة التطبيق | مسؤول Teams | رقم إصدار الحزمة ولقطة من حالة Allow |
| التخصيص لمجموعة تجريبية | مسؤول Teams | مجموعة Microsoft 365 أو مجموعة أمان مصادق عليها |
| تجربة SSO | مستخدم تجريبي + فريق المنصة | دخول، خروج، وحالة رفض غير مخول |
| الإتاحة الأوسع | مالك الأمن + مسؤول Teams | محضر اجتياز الاختبار وقبول المخاطر |

لا تعتمد هذه الخطة التوزيع الشامل تلقائياً. يبدأ التطبيق بمجموعة تجريبية محددة، ثم يراجع فريق المنصة سجلات الدخول، حدود الصلاحيات، وحالات الدعم. عند فشل تجربة SSO أو ظهور تعارض صلاحيات، يعطل مسؤول Teams التطبيق للمجموعة ثم تعود المنصة مؤقتاً إلى تشغيل الويب بحسابات التجربة غير الحساسة.

## المرحلة الرابعة: البريد المرحلي عبر Microsoft Graph

تبقى إشعارات التطبيق الداخلية هي القناة الأساسية المتاحة حالياً. عند اعتماد البريد، تستخدم المنصة صندوق بريد خدمي مملوكاً للجهة، لا صندوقاً شخصياً. تسجل الجهة الأذونات المطلوبة بحدها الأدنى، وتحفظ أسرار التطبيق في مخزن أسرار معتمد، ولا تظهر في المستودع أو سجلات المتصفح.

توفر واجهة `sendMail` في Microsoft Graph إرسال البريد باسم المستخدم أو صندوق البريد المحدد، وتتطلب إذن `Mail.Send` في نمط الصلاحية المفوض أو صلاحية التطبيق. كما أن قبول الطلب `202` لا يثبت اكتمال التسليم، ولذلك يسجل النظام محاولة الإرسال ومعرف الارتباط وحالة المعالجة، ولا يعلن وصول البريد قبل وجود تأكيد تشغيلي مناسب. [3]

| الحدث | قناة التطبيق | قناة Graph المقترحة | شرط الإرسال |
|---|---|---|---|
| إسناد مهمة جديد | إشعار فوري | نسخة اختيارية بحسب سياسة الوحدة | بعد إنشاء المهمة بنجاح |
| انتهاء المهلة الأولى | إشعار فوري | بريد للمكلف والمشرف المحدد | بعد تحقق التصعيد فعلياً |
| الإحالة الإشرافية | إشعار فوري | بريد للمشرف والرئيس بحسب السياسة | بعد إنشاء طلب المساءلة |
| مراسلة أو طلب | إشعار فوري | بريد للمستلمين في التسلسل | بعد حفظ مسار التوجيه |
| تذكرة دعم متصاعدة | إشعار فوري | بريد لمدير الدعم ثم الرئيس | بعد تحقق مهلة 72 + 24 ساعة |

## المرحلة الخامسة: Copilot Studio ضمن أقل صلاحية

ينشأ وكيل Copilot Studio منفصل عن تطبيق الويب. في الإصدار الأول تُضاف فقط مصادر معرفة مصادق عليها، مثل دليل المستخدم وإجراءات الدعم وخطة الصلاحيات. يتطلب نشر الوكيل مرة واحدة على الأقل قبل إتاحته في Teams وMicrosoft 365 Copilot؛ كما يمكن لمسؤول المؤسسة إدارة إتاحته داخل متجر Teams أو تثبيته للمجموعات المناسبة. [4]

لا يمنح الوكيل صلاحية SQL أو وصولاً مباشراً إلى S3 أو مسارات tRPC. إذا احتاج مستقبلاً إلى تنفيذ إجراء مثل الاستعلام عن حالة مهمة، ينشئ فريق المنصة واجهة API صغيرة مستقلة، مؤمنة برموز Entra، ومحددة بسيناريو واحد وصلاحية واحدة وسجل تدقيق لكل استدعاء. وتبقى مصادر SharePoint أو المعارف التي تعتمد مصادقة المستخدم محصورة في المحادثات الفردية ما لم تعتمد الجهة نموذجاً مختلفاً؛ تشير وثائق Copilot Studio إلى قيود على هذه المصادر في محادثات القنوات والمجموعات. [4]

## بوابات الاعتماد وقائمة التسليم للجهة

لا تنتقل المنصة إلى المرحلة التالية إلا عند اكتمال بوابة المرحلة السابقة. توثق الموافقة باسم المسؤول وتاريخها والبيئة والنطاق، ثم تحفظ في سجل الحركة الداخلي أو نظام التغيير المعتمد في الجهة.

| البوابة | معايير القبول | صاحب الاعتماد |
|---|---|---|
| بوابة الهوية | تطبيق Entra أحادي المستأجر، MFA، عناوين رجوع صحيحة، اختبار رفض المستخدم غير المخول | أمن المعلومات |
| بوابة الصلاحيات | خريطة تربط الحساب بالملف الداخلي ولا تمنح دوراً تلقائياً | مالك المنصة + الموارد البشرية/الإدارة |
| بوابة Teams | حزمة موقعة بالمعلومات الصحيحة، تطبيق متاح لمجموعة تجريبية فقط | مسؤول Teams |
| بوابة Graph | صندوق خدمة، `Mail.Send` بأقل نطاق متاح، سر محفوظ بأمان، اختبارات فشل وتدقيق | أمن البريد + أمن المعلومات |
| بوابة Copilot | مصادر معرفة مصنفة، اختبار منع استخراج بيانات حساسة، مسار إيقاف واضح | مالك المعرفة + Power Platform + الأمن |

## البديل الآمن عند غياب صلاحية الإدارة

إذا لم تتوفر صلاحيات Entra أو Teams أو Graph، تستمر المنصة كتطبيق ويب تجريبي مع الحسابات المؤقتة وبيانات غير حساسة فقط. تظل الإشعارات داخل التطبيق فعالة، وتبقى حزمة Teams ودليلها وخطة Microsoft 365 جاهزة للتسليم إلى قسم التقنية. لا تُحاول المنصة تجاوز سياسة Teams أو إنشاء تطبيق Entra أو قراءة ملف Teams أو إرسال بريد باسم الجهة دون تفويض رسمي.
